Cybersecurity crash course / Module 04

Operating System Security

An operating system shares one set of hardware among many programs that do not trust each other. Every confidentiality and integrity property of a running system derives from how the operating system establishes separation between those programs, between users, and between itself and the code it executes.

This module describes the mechanisms that enforce those boundaries and the techniques used to defeat them. It proceeds from the hardware privilege model up through the kernel, its interfaces, and process memory, then across the access-control, authentication, boot, and persistence layers that make up a complete system.

0x00

Threat model

The OS as a trust boundary

A computer's hardware executes whatever instructions the program counter references and returns whatever memory contents are requested. Nothing in the hardware alone prevents one program from reading another's memory or overwriting a file it does not own. Those restrictions exist because the operating system interposes on every access to hardware, and the CPU grants it the privilege to do so.

In access-control theory, this ideal component is a reference monitor: a mechanism that mediates every access to every resource, cannot be bypassed, cannot be tampered with, and is small enough to be verified. Production operating systems meet none of these criteria fully. A modern kernel is tens of millions of lines of code, which is neither small nor formally verifiable. Operating system security is largely the study of the gap between this ideal and the implementation.

Three properties an OS must provide

Isolation
Process A must not read or modify process B's memory, files, or execution state without authorization. Virtual memory, privilege rings, and namespaces enforce this.
Mediation
Access to a real resource (a file, a network socket, another process) is decided by the OS at a single chokepoint. System calls and access-control checks are where that decision occurs.
Authentication and authorization
The OS must determine on whose behalf code runs and what that identity may do. Users, credentials, tokens, and permissions encode the answer.
Privilege as the target

An attacker who compromises an application is confined to that application's privileges. An attacker who compromises the kernel controls the machine: they can read any process's memory, assume any identity, conceal their presence from monitoring tools, and persist across reboots. For this reason, gaining code execution and escalating privilege to root, SYSTEM, or the kernel are treated as distinct phases of an intrusion.

The sections that follow examine each boundary in turn. A recurring theme is the control of transitions between privilege levels. Most OS security mechanisms exist to regulate movement toward higher privilege, and most attacks attempt to force that movement.

0x01

Hardware foundation

Privilege rings and CPU modes

Software isolation depends on a hardware property: the CPU refuses to execute certain instructions unless it is in a privileged mode. This mechanism is the foundation of the operating system security model.

Every modern CPU operates at one of at least two privilege levels. On x86 these are numbered as four protection rings, from Ring 0 (most privileged) to Ring 3 (least). Operating systems use two of them:

Ring 0, kernel mode
Also called supervisor or privileged mode. Code executes any instruction, accesses all physical memory, programs the MMU, communicates with hardware, and disables interrupts. The kernel and device drivers run here.
Ring 3, user mode
Where applications run. Privileged instructions are forbidden. Attempting one raises a fault handled by the kernel. User-mode code cannot access hardware or another process's memory except through the kernel.

The CPU records the current ring in a register; on x86 this is the Current Privilege Level (CPL), held in the low bits of the code-segment selector. When user-mode code executes a privileged instruction, such as writing a control register or performing raw port I/O, the processor does not comply. It raises a general protection fault and transfers control to a kernel handler. This hardware behavior is what makes user-mode confinement enforceable rather than advisory.

Execution contexts below Ring 0

The four-ring model omits several execution contexts introduced by later hardware. These sit at higher effective privilege than Ring 0, and a compromise in any of them is not visible to the operating system:

Ring −1
Informal label for hypervisor or VMX root mode (Intel VT-x, AMD-V). A hypervisor runs here and can inspect a guest kernel executing in Ring 0. Hardware virtualization makes this efficient.
Ring −2
System Management Mode (SMM), a firmware execution mode entered by a System Management Interrupt. The OS cannot inspect it. SMM rootkits are difficult to detect and survive OS reinstallation.
Ring −3
Informal label for out-of-band management processors such as the Intel Management Engine and AMD PSP, which run on a separate microcontroller even when the main system is powered down.
Property: trust flows downward

Security guarantees depend on all lower layers. Ring 3 relies on Ring 0; Ring 0 relies on the hypervisor; all layers rely on the firmware and management engine. An attacker who reaches a lower layer defeats every protection above it. This is why firmware and hardware attacks (section 0x0B) are valuable, and why reinstalling an operating system does not remediate a firmware-level compromise.

Transitions between rings

The only legitimate way for Ring 3 code to perform a Ring 0 operation is to request it from the kernel. This transition, a mode switch, occurs on three events: a system call (the program requests a service), an interrupt (hardware signals the CPU), or an exception (the program performs an illegal operation such as dividing by zero or accessing unmapped memory). In each case the CPU switches to Ring 0, changes to a trusted kernel stack, and jumps to a fixed kernel-defined entry point rather than to an address chosen by user code. The last property is a security requirement: user code may invoke the kernel only at predetermined entry points.

0x02

The privileged core

The kernel and its attack surface

The kernel is the program that runs in Ring 0. It allocates resources, schedules execution, and enforces every permission check. Because a kernel compromise removes all other boundaries simultaneously, it is the highest-value target on the machine.

The kernel is responsible for scheduling, memory management, the filesystem and I/O stack, the network stack, inter-process communication, and permission enforcement. It also contains device drivers, which historically account for a large share of kernel vulnerabilities.

Monolithic and microkernel designs

Monolithic

Subsystems in Ring 0

Linux, Windows, and macOS's XNU are effectively monolithic: scheduler, filesystems, network stack, and drivers run in kernel mode sharing one address space. Performance is high because subsystems call one another directly. A defect in any driver is a defect in the whole kernel.

Microkernel

Services in Ring 3

seL4, QNX, and MINIX move drivers and filesystems into isolated user-mode servers, leaving only IPC, scheduling, and basic memory management in the kernel. A compromised driver cannot directly corrupt the kernel. The cost is IPC overhead. seL4 is formally verified.

Mainstream systems chose performance, so their kernels are large and their attack surface is dominated by drivers. On Windows this is exploited through a technique named Bring Your Own Vulnerable Driver (BYOVD): an attacker loads a legitimately signed but defective driver to obtain code execution in Ring 0.

Paths to kernel compromise

  • Local privilege escalation (LPE). Code already running in Ring 3 exploits a kernel defect, typically a memory-corruption bug in a syscall handler, driver, or filesystem parser, to execute instructions in Ring 0.
  • Malicious or vulnerable drivers. Loading kernel code directly. Modern operating systems require driver signing and maintain blocklists of known-vulnerable drivers.
  • Remote kernel defects. A flaw in the network stack or a protocol parser reachable from the network. MS17-010 (EternalBlue) yielded remote kernel code execution with no prior access.
Mitigations

Kernels reduce this exposure with driver signature enforcement, kernel ASLR (KASLR), and the SMEP and SMAP CPU features, which prevent the kernel from executing or reading user-mode memory and eliminate a class of exploits that redirected the kernel to attacker-controlled data. Windows adds PatchGuard (Kernel Patch Protection), which detects modification of critical kernel structures, and HVCI (Hypervisor-protected Code Integrity), which uses the hypervisor to guarantee that only signed code executes in Ring 0.

0x03

The user/kernel interface

System calls

A system call is how a Ring 3 program requests a Ring 0 service. It is the controlled interface between untrusted applications and the kernel, and therefore both the basis of isolation and a primary attack surface.

Opening a file, sending a packet, and creating a process all require privileged operations that an application cannot perform itself. The program places a syscall number and arguments in CPU registers and executes an instruction that traps into the kernel. The kernel validates the request against the caller's permissions, performs the work, and returns a result. Every effect a program has on the outside world passes through this set of a few hundred calls.

asm · x86-64 Linux · write(2)
    ; A program cannot write to the terminal directly. It requests
    ; syscall 1 (write) to send two bytes to stdout.

    mov  rax, 1          ; syscall number: 1 = sys_write
    mov  rdi, 1          ; arg0: file descriptor (1 = stdout)
    mov  rsi, msg        ; arg1: pointer to buffer
    mov  rdx, 2          ; arg2: length in bytes
    syscall             ; trap: CPU switches from Ring 3 to Ring 0
    ; the kernel validates the descriptor, the permissions, and the
    ; pointer, performs the write, and returns the count in rax.

The syscall instruction is the current fast path; older code used the software interrupt int 0x80. Windows differs in a security-relevant way: its syscall numbers are undocumented and change between builds, so programs call through ntdll.dll rather than issuing syscalls directly. Malware that issues direct syscalls does so to bypass security-product hooks placed in ntdll, evading monitoring that assumes the documented path.

Why the boundary is a security chokepoint

  • Validation. Every pointer passed to the kernel must be checked: that it references user memory, that it is mapped, and that it is adequately sized. Missing checks are a common kernel vulnerability class.
  • Permission enforcement. Whether a process may open /etc/shadow is decided inside the open syscall, not by the calling program. The check cannot be skipped because the program never executes in Ring 0.
  • Monitoring. Because meaningful actions are syscalls, observing syscalls is how endpoint detection tools, sandboxes, strace, Sysmon, and eBPF determine what a program does.
  • Confinement. Restricting which syscalls a process may issue reduces what a compromised process can do. This is the basis of seccomp (section 0x09).
Attack class: TOCTOU at the boundary

The kernel acts on behalf of the user but with its own authority, which allows it to be misdirected. In a time-of-check-to-time-of-use (TOCTOU) race, a program passes a path the kernel validates, then replaces that path with a symbolic link to a protected file after the check but before the operation. The kernel then operates on the substituted target with its own privileges. This is an instance of the confused-deputy problem. Correctly handling user-supplied references across the syscall boundary is a persistent source of kernel defects.

0x04

Isolation mechanics

Virtual memory and process isolation

Processes cannot access one another's memory because they cannot name it. Virtual memory gives each process a private address space, translated to physical memory by hardware on every access and enforced by the MMU.

Each process addresses memory from zero to the architecture's maximum as though it owned the machine. This is an abstraction maintained by the kernel and the CPU. When a program uses a virtual address, the CPU's Memory Management Unit (MMU) translates it to a physical address in RAM on every access, using page tables the kernel configured for that process.

Memory is managed in fixed-size pages, typically 4 KB. The page tables map each virtual page to a physical page or to nothing. Two properties make this the basis of isolation:

  • Separation. Each process has its own page tables. Virtual address 0x400000 in process A and the same address in process B refer to different physical memory. No virtual address process A can construct names process B's private memory.
  • Permission bits. Each page-table entry carries flags: present, writable, user-accessible, and no-execute. The MMU enforces these on every access. A write to a read-only page, or an instruction fetch from a no-execute page, faults immediately.

When a process accesses a virtual page that is not currently mapped, the MMU raises a page fault and traps into the kernel. The kernel determines the cause and responds: load the page from disk (demand paging), allocate a zeroed page (first access), copy a shared page before writing (copy-on-write), or, if the address is invalid, terminate the process with a segmentation fault. Invalid accesses producing faults rather than proceeding is isolation being enforced continuously.

Layout of a process address space

The layout encodes several security decisions. Code pages are read-only and executable. Data pages are writable and non-executable. The lowest page is left unmapped so that a null-pointer dereference faults rather than reading valid memory. The kernel is mapped into every process's high addresses but marked Ring 0 only, so user code can observe its presence while the MMU denies access.

Case study: Meltdown and KPTI

Historically the kernel was mapped into every process for performance, relying on the ring permission bit to deny access. Meltdown (disclosed 2018) exploited speculative execution: the CPU speculatively read kernel memory before completing the permission check, and although the read was architecturally discarded, it left a measurable trace in the cache that an attacker could recover bit by bit. The mitigation, Kernel Page Table Isolation (KPTI), stops mapping most of the kernel into user page tables, at a measurable performance cost. Isolation depends on hardware behaving as specified, and Meltdown demonstrated that this assumption can fail.

0x05

Exploitation and mitigation

Memory-corruption exploitation

Many system compromises reduce to a program writing outside its intended bounds and an attacker converting that error into control of execution. Exploitation techniques and the mitigations against them developed in response to one another; presenting them in order is the clearest way to understand current defenses.

C and C++ delegate memory management to the programmer. When that management is incorrect (an off-by-one error, an unchecked strcpy, a use of freed memory), a program writes where it should not. The attacker's objective is control-flow hijacking: causing the CPU to execute instructions of the attacker's choosing. The following sequence traces the exploitation and mitigation history.

Stack buffer overflow

A function stores its local buffer and its saved return address on the same stack. Overflowing the buffer overwrites the return address, and the function returns to an attacker-chosen location. The original technique, documented in 1996, placed attacker machine code (shellcode) in the buffer and overwrote the return address to point back into it. The CPU then executed the shellcode at the program's privilege level.

c · unchecked copy into a fixed buffer
void handle(char *input) {
    char buf[64];
    strcpy(buf, input);   // no bounds check; input may exceed 64 bytes
}                          // return address sits just past buf[64]

// stack layout (toward higher addresses):
//   [ buf, 64 bytes ][ saved frame ptr ][ RETURN ADDRESS ]
// a copy longer than 64 bytes overwrites the return address,
// which sets the instruction pointer on function return.

Mitigation: non-executable memory (DEP / NX / W^X)

The response marked writable memory non-executable and executable memory non-writable, a policy termed W^X (write xor execute) and enforced by the MMU's no-execute bit. It is called DEP (Data Execution Prevention) on Windows and NX elsewhere. Shellcode placed on the stack no longer runs, because an instruction fetch from a no-execute page faults. Direct code injection ceased to be viable.

Response: code reuse (return-to-libc and ROP)

If new code cannot be injected, existing executable code can be reused. Return-oriented programming (ROP) chains short sequences of existing instructions, called gadgets, each ending in a ret, by writing their addresses onto the stack. Each gadget performs a small operation and returns to the next. A sufficient set of gadgets is Turing-complete and uses only legitimately executable bytes, defeating NX. ROP remains central to current exploitation.

Mitigation: ASLR

ROP requires knowing gadget addresses. Address Space Layout Randomization randomizes the base addresses of the stack, heap, libraries, and, with position-independent executables (PIE), the program image on each run. An exploit with hardcoded addresses then references the wrong locations and crashes the target. ASLR does not fix the underlying defect; it reduces the reliability of exploitation.

Response: information disclosure

ASLR is defeated by leaking one address. A separate defect (an out-of-bounds read, an uninitialized-memory disclosure, or a format-string flaw) that reveals a single runtime address lets the attacker compute a library's base and reconstruct the ROP chain. Modern exploits therefore typically chain two defects: an information disclosure to defeat ASLR and a memory-corruption primitive to hijack control.

Additional mitigations

Stack canaries
A random value placed between local buffers and the return address. The function verifies it before returning; a linear overflow that reached the return address also altered the canary, so the program aborts. Also called stack cookies or /GS on MSVC.
RELRO
Makes the global offset table and related loader structures read-only after startup, closing a common target for converting a write into control flow.
CFI / CFG
Control-Flow Integrity records the set of valid indirect-call targets and checks them at runtime, so an indirect call or jump can only reach a legitimate function entry. Windows ships Control Flow Guard; Clang provides its own CFI.
CET / shadow stacks
Intel CET maintains a protected shadow stack of return addresses. On return, a mismatch between the normal and shadow return address faults, preventing ROP. Indirect Branch Tracking constrains indirect jumps similarly.

Heap corruption and use-after-free

Not all corruption is stack-based. Use-after-free (using a pointer to memory that has been freed and possibly reallocated) is the dominant vulnerability class in browsers and other large applications. Related classes include double-free, type confusion, and heap overflow. They are exploited by manipulating allocator behavior (heap grooming) so that a freed object is replaced with attacker-controlled data.

Direction: memory-safe languages

Each mitigation above compensates for a language that permits the defect. Microsoft and Google have both reported that roughly 70% of their severe vulnerabilities are memory-safety issues, which memory-safe languages (Rust, Go, Swift, and managed runtimes) prevent by construction. Hardware efforts such as ARM Memory Tagging Extension (MTE) add a probabilistic safety layer for existing C and C++ code. The prevailing direction is to prevent the defect rather than add further runtime mitigations.

0x06

Authorization theory

Access control models

Isolation separates processes; access control determines what a process may reach when it legitimately interacts with shared resources. Three models underlie the specific mechanisms in every operating system.

DAC
Discretionary Access Control. The owner of a resource sets its permissions and may grant access at their discretion. Unix file permissions and Windows ACLs implement this. It is flexible but does not contain a subverted process: any process running as the owner can exercise or delegate the owner's access.
MAC
Mandatory Access Control. A system-wide policy set by an administrator overrides individual owners. Subjects and objects carry labels, and the kernel enforces rules between them that no user, including root, can override at will. SELinux and AppArmor provide MAC on Linux and can confine a root process.
RBAC
Role-Based Access Control. Permissions attach to roles, and users are assigned roles. It scales administration and underlies sudo policy, Windows groups, and cloud IAM. Attribute-Based Access Control (ABAC) generalizes this using arbitrary attributes and context.

Two principles apply across all three models and account for much of practical hardening:

  • Least privilege. Each subject holds the minimum authority required for its task. A web server does not need the ability to load kernel modules.
  • Privilege separation. A program is divided so that the component requiring high privilege is small, isolated, and briefly used, while the larger and more exposed logic runs unprivileged. OpenSSH's architecture is a standard example.
0x07

Unix and Linux

Permissions and privilege escalation

On a Unix system, identity is a numeric UID, file permission is nine bits, and root is the user with UID 0. The distance between an attacker's initial foothold and full control is usually a single privilege-escalation step, and most such steps abuse the mechanisms below.

Each process runs with a UID and one or more GIDs. Files carry an owner, a group, and three permission triads (read, write, execute) for user, group, and other. UID 0 is root, historically exempt from permission checks. The kernel enforces these on each filesystem access within the relevant syscalls.

sh · permission bits and the setuid flag
$ ls -l /etc/shadow /usr/bin/passwd
-rw-r----- 1 root shadow  /etc/shadow      # only root may read the hashes
-rwsr-xr-x 1 root root    /usr/bin/passwd  # 's' in place of 'x': setuid

# The setuid bit makes passwd run as its owner (root) rather than
# as the invoking user, so an ordinary user can update the
# root-owned shadow file. passwd restricts edits to the caller's
# own entry, so the elevated privilege is narrowly scoped.

The setuid mechanism

The setuid bit is central to Unix privilege escalation. A setuid-root binary runs specific code as root on behalf of an unprivileged user, which is required by tools such as passwd, sudo, and ping. Each such binary is also a privilege boundary an attacker can target. If it contains a memory-corruption defect, mishandles an environment variable, trusts PATH, or can be induced to spawn a shell, the attacker obtains UID 0. Enumerating setuid binaries with find / -perm -4000 is a standard step in both hardening and attack.

Common escalation vectors

Vulnerable setuid binary
Exploiting a defect in a trusted program. CVE-2021-4034 (PwnKit, in pkexec) produced root from any account.
Kernel LPE
A defect in a syscall or driver, such as Dirty COW or Dirty Pipe, that allows unprivileged code to corrupt kernel memory or protected files and become root.
Sudo misconfiguration
A rule permitting a user to run one program as root where that program can spawn a shell, write files, or execute code (for example vim, find, or tar). The GTFOBins project catalogs these.
Weak file permissions
A world-writable script run by root via cron, a writable PATH directory, or an unquoted service path. The attacker places code that a privileged context later executes.
Excessive capabilities
A binary granted a capability such as cap_setuid (section 0x09) can be used to become root without the setuid bit.
Intrusion structure

Most intrusions follow the same sequence: obtain code execution as a low-privileged user (a service account or a logged-in user), escalate to root or SYSTEM, then optionally escalate to the kernel to persist and conceal activity. The escalation steps are where OS security mechanisms are intended to hold and where misconfiguration removes them.

0x08

Windows internals

The Windows security model

Windows uses a more granular model than Unix. Identity is a variable-length SID, each process carries an access token describing its rights, and access to most objects is checked against a detailed access-control list. The additional expressiveness also increases the configuration surface.

SIDs, tokens, and the access check

Each security principal (user, group, computer, or service) is identified by a Security Identifier (SID), for example S-1-5-21-…-1001. At logon, the LSASS process constructs an access token containing the user's SID, group SIDs, and privileges. Every process the user launches carries a copy of this token, which constitutes its identity to the kernel.

Securable objects (files, registry keys, processes, named pipes, services) carry a security descriptor containing a DACL, an ordered list of access-control entries (ACEs) that allow or deny specific rights to specific SIDs. On an access request, the Security Reference Monitor evaluates the DACL against the token and grants the matching rights. A separate SACL governs auditing.

Privileges
Token-carried rights distinct from object permissions, such as SeDebugPrivilege (open any process), SeBackupPrivilege (read any file), and SeImpersonatePrivilege (act under another token, the basis of the "Potato" escalation family for service accounts).
Integrity levels
A mandatory-integrity layer above DACLs. Objects and processes receive a level (Low, Medium, High, System). A Low-integrity process, such as a sandboxed browser tab, cannot write to higher-integrity objects even where the DACL would permit it.
UAC
User Account Control. Administrators run with a filtered Medium-integrity token for routine work and receive the full High-integrity token only after an elevation prompt. Microsoft states that UAC is not a security boundary, which is why UAC bypasses are fixed but not treated as full vulnerabilities.
Attack: credential theft from LSASS

Because LSASS performs authentication, its memory can contain credential material: NTLM hashes, Kerberos tickets, and, on older configurations, cleartext passwords. Tools such as Mimikatz read LSASS memory to extract these, enabling pass-the-hash and pass-the-ticket lateral movement without cracking a password. Defenses include Credential Guard, which isolates secrets in a hypervisor-protected enclave, LSASS run as a protected process (PPL), and hardened LSA configuration. Compromise of a single administrative host frequently leads to domain-wide compromise through this path.

Kernel-mode protections

On 64-bit Windows the kernel is protected by PatchGuard, which periodically verifies that critical kernel structures have not been modified; Driver Signature Enforcement; and, when enabled, HVCI (Memory Integrity), which uses the hypervisor to ensure no unsigned page is executable in kernel mode. With virtualization-based security (VBS), these move key trust decisions below Ring 0, where a kernel-mode compromise cannot readily reach them.

0x09

Confinement primitives

Linux hardening primitives

The all-or-nothing authority of UID 0 is a liability. Modern Linux divides it into finer mechanisms: capabilities, namespaces, seccomp, and Linux Security Modules. These can confine a root process, and together they constitute the building blocks of containers.

Capabilities

Rather than a single omnipotent UID 0, Linux capabilities divide root's authority into about 40 units. A process holds only those it requires: CAP_NET_BIND_SERVICE to bind a port below 1024, CAP_NET_RAW for raw sockets, CAP_SYS_ADMIN for a broad set of administrative operations. This allows a web server to bind a low port without also being able to load kernel modules or read arbitrary files. Two cautions apply: CAP_SYS_ADMIN is broad enough to approximate root, and several capabilities, including CAP_SYS_MODULE and CAP_DAC_OVERRIDE, can be escalated to full root, so granting them is close to granting root.

Namespaces and cgroups

A namespace virtualizes a kernel resource so that processes inside it see an isolated view. The types include PID (process tree), NET (interfaces and routing), MNT (mounts), UTS (hostname), IPC, USER, and cgroup. Control groups (cgroups) limit and account for resource use such as CPU, memory, and I/O. Namespaces, cgroups, and a restricted root filesystem together form a container. A container is not a virtual machine: it is a set of kernel features sharing a single kernel with the host.

Attack surface: the shared kernel

Every container on a host uses the same kernel. A single kernel vulnerability, or a misconfiguration such as a privileged container, a mounted Docker socket, or an over-broad capability, can allow a process to escape the container and reach the host and sibling containers. User namespaces allow unprivileged users to create containers, which supports least privilege but has historically expanded kernel attack surface by making formerly root-only code reachable by any user. A container's isolation boundary is weaker than a virtual machine's, and threat models should reflect this.

seccomp

Because a process's effects flow through syscalls (section 0x03), restricting the available syscalls restricts what a compromised process can do. seccomp-bpf installs a filter that limits which syscalls a process may issue, and with which argument values, for the remainder of its lifetime. A media parser that needs only read, write, and exit can forbid the rest, so that even after full compromise the attacker cannot call execve or socket. seccomp underlies the sandboxes in Chrome, systemd, and container runtimes.

Linux Security Modules

The Linux Security Module (LSM) framework adds mandatory access control on top of standard DAC checks. SELinux labels every subject and object and enforces type-enforcement rules strict enough to confine a root process to the files and ports its role permits, containing a compromised daemon. AppArmor uses a simpler path-based policy that is easier to author. In both cases the mandatory policy, which root cannot casually override, limits the effect of a compromise.

Composition

These primitives combine. A service can run as a non-root user, hold only the two capabilities it needs, run within namespaces, be filtered by seccomp, and be confined by an SELinux policy. Each layer is imperfect alone; together they ensure that a defect in the service is not a defect in the whole system. A well-configured systemd unit or container sandbox applies exactly this layering.

0x0A

Identity and secrets

Authentication and credential storage

Before authorizing an action, the OS must authenticate the principal. How it stores and verifies credentials determines the impact of a stolen credential database.

An operating system must not store passwords in a recoverable form. It stores a salted hash: the password processed through a deliberately slow one-way function together with a unique random salt. At login, the OS hashes the submitted password and compares. The salt ensures that identical passwords produce different hashes, defeating precomputed rainbow tables, and the slowness raises the cost of brute-force search.

/etc/shadow · stored credential format
alice:$y$j9T$Xf3n…salt…$Rk8…hash…:19700:0:99999:7:::
      └┬┘    └──┬──┘ └──┬──┘
     algorithm  salt     hash

# $y$       yescrypt (default on current distributions)
# $6$       SHA-512-crypt (older default)
# $2b$      bcrypt        $argon2id$  current recommended choice
# File mode 640, owner root:shadow; unreadable to normal users.
# If the file leaks, offline cracking begins against every hash.

The choice of hash function is a security decision. Fast general-purpose hashes (MD5, plain SHA-256) are unsuitable for passwords precisely because a GPU can compute billions per second. Purpose-built password hashes (bcrypt, scrypt, yescrypt, and Argon2id) are slow and memory-hard to resist GPU and ASIC attacks. On Linux, PAM (Pluggable Authentication Modules) coordinates hashing, password policy, lockout, and multi-factor authentication.

Windows

SAM, NTLM, Kerberos

Local hashes reside in the SAM database; domain hashes in NTDS.dit on domain controllers. The legacy NT hash is unsalted MD4, which is fast to crack and usable directly in pass-the-hash without cracking. Kerberos is the domain authentication protocol; ticket-based attacks (Kerberoasting, Golden and Silver Tickets) target it.

The offline threat

Dependence on file permissions

Every protection here assumes the attacker cannot read the hash storage. Once they can, via a backup, a volume shadow copy, a raw-disk read, or LSASS memory, runtime checks are irrelevant and the problem becomes offline cracking. This links authentication to storage encryption (0x0C) and file permissions (0x07).

Beyond passwords

OS authentication is moving away from shared secrets toward biometrics gated by secure hardware (Apple Secure Enclave, Windows Hello with the TPM), hardware security keys implementing FIDO2/WebAuthn, and certificate or smart-card logins. These share a hardware root of trust that the OS software cannot extract, moving the secret out of crackable storage into hardware designed to resist extraction.

0x0B

Below the OS

Boot chain and firmware security

The defenses described so far assume the running OS is the one the operator intends to run. Code that executes before the OS can compromise everything that follows. Boot security addresses the trustworthiness of the code that loads the kernel.

At power-on the CPU executes firmware (UEFI, the successor to legacy BIOS) from a flash chip. Firmware initializes hardware, then loads the bootloader, which loads the kernel, which starts user space. Each stage transfers control to the next. An attacker who subverts an early stage controls all later stages and, because they run before the OS and its security tools, is difficult to detect from within the OS. Malware at these stages is named accordingly: a bootkit in the bootloader, or a UEFI rootkit in firmware. Both can survive OS reinstallation and disk replacement.

Secure Boot

Secure Boot requires each stage to be cryptographically signed and verifies the signature before execution. The firmware holds trusted keys and refuses to run a bootloader not signed by a trusted authority; a Secure Boot-aware bootloader refuses an unsigned kernel; and so on. The result is a chain of trust anchored in firmware. It verifies that code is the code the vendor signed, not that the code is free of defects, but it prevents a class of unsigned bootkits from loading.

TPM and measured boot

A Trusted Platform Module (TPM) is a dedicated security chip that adds two capabilities. In measured boot, each stage's hash is recorded into the TPM's tamper-resistant Platform Configuration Registers (PCRs) by an operation that can extend but not rewind them, producing a fingerprint of exactly what booted. In sealing, the TPM can bind a secret, such as a disk-encryption key, so that it is released only when the PCRs match a known-good state; a modified bootloader changes the PCRs and the key is not released. With remote attestation, a machine can prove to a server which software it booted.

Distinction: Secure Boot vs. measured boot

The two are complementary. Secure Boot is preventive and local: it refuses to execute unsigned code. Measured boot is evidentiary: it does not block execution but produces an unforgeable record of what ran, on which a later decision (release a key, admit a device to a network) can be based. Firmware attacks such as LoJax, the first UEFI rootkit found in the wild, and BlackLotus, which bypassed Secure Boot, motivate continued hardening of this layer and the migration of the ultimate root of trust into hardware the OS cannot rewrite.

0x0C

Data at rest

Storage encryption

Access control is enforced only while the OS is running. A disk removed and attached to another machine exposes its files, because permissions are metadata that the attacker's OS need not honor. Full-disk encryption addresses physical access to storage.

Full-disk encryption (FDE) encrypts an entire volume so that, without the key, its contents are indistinguishable from random data. LUKS/dm-crypt (Linux), BitLocker (Windows), and FileVault (macOS) operate transparently in the block layer beneath the filesystem, decrypting on read and encrypting on write. The relevant question is where the key resides and what releases it.

Passphrase-derived
The key is derived from a passphrase through a slow key-derivation function. Security depends on passphrase strength. The user enters it at boot. No hardware dependency.
TPM-sealed
The key is sealed to the TPM and released automatically only if measured boot (0x0B) indicates an untampered system. Boot is seamless, but the key resides in memory once booted, and TPM-only mode has known attack avenues.
TPM plus PIN
Requires both the TPM's release and a user PIN, defeating attacks that rely on capturing an automatically released key. This is the recommended configuration for portable devices holding sensitive data.
Scope: FDE protects only a powered-off disk

Encryption at rest protects the at-rest state and nothing further. Two attacks illustrate the limits. In a cold-boot attack, DRAM retains its contents for seconds after power loss; an attacker cools the RAM, reboots to a minimal OS, and reads the encryption key from memory. In an evil-maid attack, brief physical access is used to modify the unencrypted bootloader to capture the passphrase on the next boot, which is the threat Secure Boot and measured boot address. Once the system is booted and unlocked, FDE provides no protection against a running-system compromise and does not substitute for the other layers.

0x0D

Post-exploitation

Rootkits, injection, and persistence

After gaining access, an attacker generally seeks to remain resident and undetected. The techniques for doing so reuse the OS mechanisms described earlier, viewed from the attacker's side.

Code injection

Rather than launch a new process, attackers often run code inside an existing trusted process. On Windows the common techniques are DLL injection (causing a target process to load a library, typically via CreateRemoteThread and LoadLibrary), process hollowing (starting a legitimate process suspended, replacing its memory with malicious code so it appears legitimate in the process list), APC injection, and reflective loading (mapping a payload into memory with no file on disk). On Linux, LD_PRELOAD and ptrace serve comparable purposes. Each abuses the ability of one process to write another's memory, an ability the OS grants to debuggers and thus to holders of SeDebugPrivilege or root.

Rootkits

A rootkit is malware whose function is to conceal itself and often other malware. Its location determines how difficult it is to detect and remove:

User-mode rootkit
Hooks user-space API calls to filter what tools display, hiding files, processes, or connections. Easiest to implement and to detect, since a tool that queries the kernel directly bypasses the modified API.
Kernel-mode rootkit
Runs in Ring 0 and can alter what all tools observe, because it operates beneath them. Techniques include SSDT hooking (redirecting syscall handlers) and Direct Kernel Object Manipulation (DKOM), such as unlinking a process from the kernel's process list so it runs without appearing. Driver signing and PatchGuard target this class.
Firmware or hypervisor rootkit
Resides in UEFI, SMM, the management engine, or a malicious hypervisor beneath the OS (Rings −1 to −2 of section 0x01). Survives OS reinstallation and disk replacement and is not visible to OS-level defenses.

Persistence

To retain access, malware attaches to a mechanism the OS runs automatically at startup or on a schedule. The options are OS-specific: on Windows, Run keys, scheduled tasks, services, WMI event subscriptions, and DLL search-order hijacking; on Linux, systemd units, cron jobs, .bashrc, udev rules, and kernel modules. Each is a legitimate OS feature repurposed as a re-execution hook, which is why defenders monitor these locations, enumerated in frameworks such as MITRE ATT&CK.

Principle: a compromised host cannot report reliably on itself

The deeper an attacker's access, the more completely they control what local tools observe. Reliable detection therefore increasingly originates outside the OS: hypervisor-based introspection, out-of-band network monitoring, TPM attestation, and immutable off-host logging. A confirmed kernel or firmware rootkit is generally remediated by reimaging from known-good media rather than by cleaning in place.

0x0E

Isolation at scale

Virtualization and containers

The same isolation principles that separate processes are applied one level higher to separate whole operating systems, and adjacently to separate applications at lower cost. The strength of each boundary differs, which matters for any threat model.

Virtual machines

A hypervisor does for operating systems what the kernel does for processes: it gives each guest OS the appearance of dedicated hardware, mediated in a more-privileged layer (Ring −1). A Type 1 hypervisor (ESXi, Hyper-V, KVM) runs on bare metal; a Type 2 hypervisor (VirtualBox, VMware Workstation) runs on a host OS. Hardware virtualization (VT-x, AMD-V) makes this efficient by trapping sensitive guest operations directly to the hypervisor. Because each VM has its own kernel and the hypervisor's interface to the guest is comparatively narrow, isolation is strong: a full guest compromise is contained within the guest.

Attack: VM escape

A VM escape exploits a defect in the hypervisor or, more commonly, its emulated devices to execute code in the host or hypervisor, collapsing the boundary between tenants. VENOM, a defect in QEMU's virtual floppy controller, is the standard example. The emulated-device surface is the softest part of a hypervisor, so minimizing exposed virtual hardware is standard hardening.

Containers

As established in section 0x09, a container is namespaces, cgroups, and a confined root filesystem sharing the host's single kernel. Containers are lightweight because no second OS boots, but the isolation boundary is the kernel's full syscall interface rather than a hypervisor's narrow one. A kernel defect reachable from inside a container is a potential host compromise.

Virtual machine

Separate kernel

Boundary is the hypervisor and its narrow device interface. Escape requires a hypervisor defect. Heavier and slower to start, with stronger isolation. Appropriate for hostile multi-tenancy.

Container

Shared kernel

Boundary is the host kernel's full syscall surface. Escape requires a kernel defect or misconfiguration. Light and fast, with weaker isolation. Suitable for trusted workloads, higher-risk for hostile ones.

To combine container efficiency with stronger isolation, intermediate designs place each workload in a reduced-surface layer. gVisor interposes a user-space kernel to limit the host syscall surface a container can reach; Firecracker and Kata Containers wrap workloads in stripped-down virtual machines. Each represents an explicit trade-off along the isolation-versus-overhead axis.

0x0F

Visibility

Logging, auditing, and forensics

Prevention is not complete. When it fails, the ability to reconstruct events determines whether an incident is contained or undetected for an extended period. Logging is the control that provides value after a compromise.

Operating systems can record which principal performed which action, when, and on what object. On Linux, auditd captures syscall-level events against configurable rules, journald and syslog hold system and service logs, and eBPF-based tooling provides low-overhead runtime visibility. On Windows, the Event Log carries Security, System, and Application channels covering logon events, privilege use, and process creation, and Sysmon adds detailed process, network, and image-load telemetry.

Forensic artifacts

Beyond deliberate logs, ordinary OS operation records data used in investigations. On Windows: Prefetch (evidence a program executed), Shimcache and Amcache (execution history), the $MFT and USN journal (file creation and change records), registry hives, and shellbags (browsed folders). On Linux: shell histories, /var/log, systemd journals, and filesystem timestamps. Volatile memory holds additional state: a RAM capture can recover encryption keys, injected code, network connections, and process state that never reached disk, which is the basis of memory forensics (for example, with Volatility).

Practice: logs the attacker cannot alter

A capable intruder clears logs and disables auditing early, so logs stored only on the compromised host are only as trustworthy as the host. The countermeasures are architectural: ship logs off-host in real time to a system the attacker cannot reach, store them append-only or immutable, and alert on the event that indicates logging was stopped. A sudden absence of expected log volume is itself an indicator of compromise.

0x10

Summary

Hardening principles

The mechanisms in this module reduce to a small set of principles applied consistently. Specific tools and vulnerabilities are instances of these patterns.

Least privilege
Run every process, user, and service with the minimum authority required: non-root services, dropped capabilities, filtered syscalls, and scoped tokens. This is the highest-leverage practice, because it converts compromises into contained ones.
Reduce attack surface
Every running service, open port, installed package, and loaded driver can contain a defect. Disable, uninstall, and unmap what is not in use.
Defense in depth
Assume each layer can fail and stack independent layers so that no single failure is decisive: MMU isolation, ASLR, seccomp, MAC, and monitoring together.
Patch promptly
Most exploited kernel and privilege-escalation defects are known and fixed before they are widely exploited. Timely patching closes the exposure window.
Secure the boot chain
Enable Secure Boot, TPM-backed encryption, driver signing, and code-integrity enforcement, anchoring trust in hardware the OS cannot rewrite.
Assume breach and retain evidence
Design as though an attacker is already present: segment, monitor, and log off-host immutably so that a compromise can be detected, scoped, and remediated.
Unifying observation

Most of this module concerns the control of movement between privilege levels: keeping Ring 3 out of Ring 0, one user out of another's memory, a container out of the host, and software out of firmware. Attackers work to move inward and downward; defenders work to make each boundary enforceable, layered, and observable. The location and enforcement of these boundaries is the organizing structure for the rest of the field.
